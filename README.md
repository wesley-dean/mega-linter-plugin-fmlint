This MegaLinter plugin lints YAML frontmatter at the beginning of Markdown
documents.  A thin `fmlint` adapter extracts the frontmatter and delegates the
actual YAML analysis to [yamllint](https://github.com/adrienverge/yamllint).
Markdown after the closing frontmatter delimiter is never passed to yamllint.

## Frontmatter Contract

A document has YAML frontmatter when its first line is:

```text
---
```

The first subsequent standalone `---` line closes the frontmatter.  For
example:

```markdown
---
title: Example
tags:
  - documentation
  - example
---

# Markdown starts here

This content is not YAML and does not affect the frontmatter lint result.
```

Markdown files without an opening frontmatter delimiter are ignored.  An opening
delimiter without a closing delimiter is reported as malformed frontmatter.

## MegaLinter Configuration

Released descriptors are the supported distribution channel for normal
MegaLinter use.  For reproducible CI and production workflows, pin the plugin to
a specific release:

```yaml
PLUGINS:
  - "https://github.com/wesley-dean/mega-linter-plugin-fmlint/releases/download/v0.1.0/fmlint.megalinter-descriptor.yml"
```

When deliberately following the newest released version, use the latest-release
asset:

```yaml
PLUGINS:
  - "https://github.com/wesley-dean/mega-linter-plugin-fmlint/releases/latest/download/fmlint.megalinter-descriptor.yml"
```

Pinning a release is preferred when build reproducibility matters.  The
`releases/latest/download/` form trades that reproducibility for automatic
adoption of newly published fmlint releases.

Each GitHub release also includes
`fmlint.megalinter-descriptor.yml.sha256`.  The checksum detects byte changes
when the expected checksum is obtained from a trusted release context.

The descriptor stored on the repository's `main` branch remains useful for
plugin development and testing, but it follows development state and is not the
recommended production distribution mechanism.

Depending on the rest of your MegaLinter configuration, explicitly enable the
linter when necessary:

```yaml
ENABLE_LINTERS:
  - "MARKDOWN_FMLINT"
```

The descriptor uses MegaLinter's content filtering to select Markdown files that
begin with a frontmatter delimiter.  Existing
`MARKDOWN_FMLINT_FILTER_REGEX_INCLUDE` and
`MARKDOWN_FMLINT_FILTER_REGEX_EXCLUDE` settings remain available when a
repository wants to narrow that set further.

## yamllint Configuration

The default configuration file is `.fmlint.yml`.  It uses yamllint's ordinary
configuration syntax, so a repository may give frontmatter different YAML style
rules from its standalone YAML documents.

MegaLinter's generated configuration variable for overriding that path is
`MARKDOWN_FMLINT_CONFIG_FILE`.

## Releases

A release contains:

```text
fmlint.megalinter-descriptor.yml
fmlint.megalinter-descriptor.yml.sha256
```

The distributed descriptor is generated from the maintained descriptor and pins
its runtime downloads to the exact Git commit that produced the release.  That
means the released descriptor, `fmlint.bash`, and `requirements.txt` resolve
to one immutable source revision even though the development descriptor follows
`main`.

Release validation exercises the generated descriptor through MegaLinter before
the GitHub release is created.  The validated files are transferred to a
separate publication job and their checksum and exact file set are verified again
before publication.

## Development

The maintained adapter is `fmlint.bash`.  Behavioral tests use Bats and keep TAP
as the canonical console format while writing derivative JUnit data beneath
`test-results/`.

Useful targets are:

```bash
make test
make validate
make build
make validate-release
make integration-test
make clean
```

`make test` runs deterministic wrapper and release-build tests.
`make validate` checks the maintained descriptor against the schema from the
pinned MegaLinter release.  `make build` creates a commit-pinned release
descriptor and SHA-256 checksum beneath `dist/`.  `make validate-release`
validates those generated bytes and their checksum.  `make integration-test`
loads the generated descriptor through MegaLinter and exercises real yamllint
behavior.

For a local release-style build, supply the version and source commit explicitly:

```bash
make build VERSION=0.1.0 BUILD_REF="$(git rev-parse HEAD)"
```

## Repository Governance

This repository adopts released engineering standards from
[`wesley-dean/coding_standards`](https://github.com/wesley-dean/coding_standards).
The complete pinned snapshot is committed beneath `doc/standards/`, while
`.codingstandardrc` records the adopted release and verified archive digest.

Applicable files beneath `doc/standards/` are project requirements, subject to
accepted repository-specific ADRs and explicit local policy.  Imported standards
are managed as a release snapshot and are not edited locally to create
project-specific exceptions.
